## 2. Аналіз інструментів перевірки

### 2.1 Hadolint (Лінтер)
**Типи перевірок:**
- Синтаксичні помилки Dockerfile
- Стилістичні порушення
- Best practices (ADD vs COPY, apt-get cache, pinning versions)

**Виявлені проблеми в Docker-bad:**
- `DL3020`: Використання ADD замість COPY
- `DL3008`: Відсутність фіксації версій пакетів
- `DL3009`: Відсутність очищення apt кешу після встановлення
- `DL3015`: Уникнення apt-get upgrade/dist-upgrade в контейнерах

### 2.2 Trivy (Сканер безпеки)
**Типи перевірок:**
- Конфігураційні вразливості
- Порушення безпеки (запуск від root, відсутність HEALTHCHECK)
- Потенційні шляхи ескалації привілеїв

**Виявлені проблеми в Docker-bad:**
- **HIGH**: Запуск контейнера від користувача root
- **MEDIUM**: Відсутність HEALTHCHECK для моніторингу стану
- **LOW**: Небезпечне використання apt-get без --no-install-recommends

### 2.3 Dockle (Аудитор best practices)
**Типи перевірок:**
- Відповідність CIS Docker Benchmark
- Оптимізація розміру образу
- Наявність зайвих файлів і кешів

**Виявлені проблеми в Docker-bad:**
- `CIS-DI-0001`: Відсутність непривілейованого користувача
- `CIS-DI-0006`: Відсутність HEALTHCHECK інструкції
- `DKL-DI-0005`: Не видалено apt кеш після встановлення пакетів

## 3. Порівняльний аналіз Docker-bad vs Docker-good

### 3.1 Критичні порушення безпеки в Docker-bad

| № | Порушення | Рівень ризику | Наслідки |
|---|-----------|---------------|----------|
| 1 | Запуск від root | **КРИТИЧНИЙ** | Якщо контейнер скомпрометовано, зловмисник отримує root-права |
| 2 | Використання ADD замість COPY | Середній | ADD автоматично розпаковує архіви - непередбачувана поведінка |
| 3 | Відсутність --no-install-recommends | Середній | Збільшення розміру образу, більша поверхня атаки |
| 4 | Відсутність HEALTHCHECK | Середній | Неможливість автоматичного визначення проблем з контейнером |
| 5 | Не видалено apt кеш | Низький | Збільшення розміру образу на десятки MB |

### 3.2 Виправлення в Docker-good

```dockerfile
# ❌ Docker-bad
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y curl
ADD . /app

# ✅ Docker-good
FROM debian:12.5-slim
RUN apt-get update && \
    apt-get install -y --no-install-recommends && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*
COPY . /app
```

**Ключові виправлення:**
1. ✅ Використання slim-образу (debian:12.5-slim)
2. ✅ Додано `--no-install-recommends`
3. ✅ Очищення кешу apt
4. ✅ Створення непривілейованого користувача (`useradd -m -s /bin/bash safeuser`)
5. ✅ Перемикання на користувача (`USER safeuser`)
6. ✅ Додано HEALTHCHECK
7. ✅ Додано LABEL для документування

## 4. Поведінка GitLab CI/CD Pipeline

### 4.1 Конфігурація allow_failure

```yaml
hadolint:
  allow_failure: true   # Pipeline продовжиться навіть при помилках

trivy:
  allow_failure: false  # Pipeline зупиниться при виявленні проблем

dockle:
  allow_failure: false  # Pipeline зупиниться при виявленні проблем
```

### 4.2 Реакція системи

**При перевірці Docker-bad:**
- Hadolint: ⚠️ Попередження (pipeline продовжується)
- Trivy: ❌ Помилка (exit code 1, pipeline зупиняється)
- Dockle: ❌ Помилка (exit code 1, pipeline зупиняється)

**При перевірці Docker-good:**
- Hadolint: ✅ Успіх
- Trivy: ✅ Успіх
- Dockle: ✅ Успіх

## 5. Відповіді на ключові питання

### 5.1 Які типи перевірок виконує кожен інструмент?

- **Hadolint**: Синтаксис, стиль, best practices Dockerfile
- **Trivy**: Безпека конфігурації, вразливості, ризики
- **Dockle**: CIS benchmarks, оптимізація, production-ready перевірки

### 5.2 Як GitLab реагує на порушення?

GitLab використовує exit code для визначення успішності job:
- Exit code 0 = успіх
- Exit code 1 = помилка (job fails)
- `allow_failure: true` дозволяє pipeline продовжитися навіть при помилках

### 5.3 Які практики вважаються безпечними?

1. **Непривілейований користувач** - обов'язково створювати USER
2. **Slim образи** - мінімізація поверхні атаки
3. **HEALTHCHECK** - моніторинг стану контейнера
4. **Очищення кешу** - оптимізація розміру
5. **COPY замість ADD** - явне керування файлами
6. **--no-install-recommends** - встановлення лише необхідних пакетів
7. **Multi-stage builds** - поділ build/runtime середовища

### 5.4 Які порушення є критичними для безпеки?

**Критичні:**
1. Запуск від root - найбільший ризик ескалації привілеїв
2. Встановлення пакетів з невідомих джерел
3. Відсутність валідації вхідних даних

**Важливі:**
4. Відсутність HEALTHCHECK
5. Використання latest тегів
6. Відкриття непотрібних портів

### 5.5 Як змінюється поведінка pipeline при різних рівнях помилок?

- **allow_failure: false** - pipeline зупиняється, merge request блокується
- **allow_failure: true** - pipeline продовжується, але помилка видима
- Це дозволяє поступово впроваджувати нові правила без блокування розробки

### 5.6 Чому важливо запускати всі три інструменти?

Кожен інструмент має свою спеціалізацію:
- **Hadolint** ловить синтаксичні помилки на ранній стадії
- **Trivy** аналізує безпеку конфігурації
- **Dockle** перевіряє production-ready стандарти

Разом вони дають повне покриття:
```
Hadolint → Синтаксис і стиль
    ↓
Trivy → Безпека конфігурації
    ↓
Dockle → Production readiness
```

### 5.7 Як створити безпечний Dockerfile?

**Checklist для безпечного Dockerfile:**

- [ ] Використовувати slim/alpine базові образи
- [ ] Фіксувати версії образів (не використовувати `latest`)
- [ ] Створити непривілейованого користувача
- [ ] Додати HEALTHCHECK
- [ ] Очищати apt/apk кеш після встановлення
- [ ] Використовувати COPY замість ADD
- [ ] Використовувати --no-install-recommends
- [ ] Мінімізувати кількість RUN шарів
- [ ] Додати LABEL для документування
- [ ] Не зберігати секрети в образі
- [ ] Використовувати .dockerignore

## 6. Практичні рекомендації

### 6.1 Інтеграція в CI/CD

1. **Hadolint** на стадії lint - з `allow_failure: true` для поступового впровадження
2. **Trivy** на стадії scan - з `allow_failure: false` для блокування критичних проблем
3. **Dockle** на стадії audit - для фінальної перевірки перед деплоєм

### 6.2 Автоматизація

```yaml
# Приклад строгої перевірки
trivy:
  script:
    - trivy config --severity HIGH,CRITICAL --exit-code 1 $DOCKERFILE_PATH
```

### 6.3 Моніторинг

- Зберігати артефакти звітів (dockle-report.json)
- Відстежувати тренди змін метрик безпеки
- Інтегрувати з системами оповіщення

## 7. Висновки

1. **Автоматизована перевірка безпеки** є критично важливою для production-середовищ
2. **Кожен інструмент відповідає за свою область** - комплексний підхід необхідний
3. **Найкритичніша проблема** - запуск контейнерів від root
4. **GitLab CI/CD дозволяє** гнучко налаштовувати рівні строгості перевірок
5. **Безпечний Dockerfile** вимагає дотримання множини best practices одночасно

**Практичний результат:** Docker-good проходить усі перевірки та може використовуватися у production, тоді як Docker-bad блокується на етапі CI/CD.
