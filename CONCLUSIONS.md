# Висновки по лабораторній роботі

## 🎯 Основні висновки

### 1. Які типи перевірок виконує кожен інструмент?

#### **Hadolint** 
**Роль:** Лінтер Dockerfile  
**Перевіряє:**
- ✓ Синтаксичні помилки
- ✓ Стилістичні порушення  
- ✓ Best practices (ADD vs COPY, apt-get правила)
- ✓ Фіксація версій пакетів
- ✓ Формат команд (JSON vs shell)

**Приклад знахідок:**
- `DL3020`: Використано ADD замість COPY
- `DL3009`: Не видалено apt кеш
- `DL3008`: Не зафіксовано версії пакетів

---

#### **Trivy**
**Роль:** Сканер безпеки конфігурацій  
**Перевіряє:**
- ✓ Конфігураційні вразливості
- ✓ Ризики безпеки (запуск від root)
- ✓ Відсутність HEALTHCHECK
- ✓ Небезпечне використання системних команд
- ✓ Потенційні шляхи ескалації привілеїв

**Приклад знахідок:**
- `HIGH`: Контейнер працює від root - критичний ризик
- `MEDIUM`: Відсутній HEALTHCHECK - неможливо відстежити стан
- `LOW`: apt-get без --no-install-recommends

---

#### **Dockle**
**Роль:** Аудитор відповідності CIS Docker Benchmark  
**Перевіряє:**
- ✓ Відповідність CIS стандартам
- ✓ Production-готовність образу
- ✓ Оптимізація розміру
- ✓ Наявність зайвих файлів і кешів
- ✓ Правильність налаштування користувача

**Приклад знахідок:**
- `CIS-DI-0001` (FATAL): Не створено користувача
- `CIS-DI-0006` (WARN): Відсутній HEALTHCHECK
- `DKL-DI-0005` (INFO): Не видалено apt кеш

### 2. Як GitLab реагує на порушення?

GitLab використовує **exit code** для визначення успішності job:

```yaml
allow_failure: false  →  Exit code 1 зупиняє pipeline ❌
allow_failure: true   →  Pipeline продовжується з попередженням ⚠️
```

**Поведінка для Docker-bad:**
- `hadolint` (allow_failure: true) → ⚠️ Попередження, pipeline продовжується
- `trivy` (allow_failure: false) → ❌ ПОМИЛКА, pipeline ЗУПИНЯЄТЬСЯ
- `dockle` (allow_failure: false) → ❌ ПОМИЛКА, pipeline ЗУПИНЯЄТЬСЯ

**Результат:** Merge request блокується, деплой неможливий.

**Поведінка для Docker-good:**
- Всі три job → ✅ SUCCESS
- Pipeline завершується успішно
- Можливий деплой у production

### 3. Які практики вважаються безпечними?

#### 🔒 **Критично важливі практики:**

1. **Непривілейований користувач**
   ```dockerfile
   RUN useradd -m -s /bin/bash appuser
   USER appuser
   ```
   **Чому:** Захист від ескалації привілеїв при компрометації контейнера.

2. **HEALTHCHECK для моніторингу**
   ```dockerfile
   HEALTHCHECK --interval=30s CMD curl --fail http://localhost/health || exit 1
   ```
   **Чому:** Kubernetes/Docker Swarm можуть автоматично перезапускати "мертві" контейнери.

3. **Slim образи**
   ```dockerfile
   FROM debian:12.5-slim  # Замість ubuntu:22.04
   ```
   **Чому:** Менший розмір = менше вразливостей = менша поверхня атаки.

#### 🛡️ **Важливі практики:**

4. **Очищення кешів**
   ```dockerfile
   RUN apt-get clean && rm -rf /var/lib/apt/lists/*
   ```
   **Чому:** Зменшення розміру образу на 40-100 MB.

5. **--no-install-recommends**
   ```dockerfile
   RUN apt-get install -y --no-install-recommends curl
   ```
   **Чому:** Встановлення лише необхідних пакетів.

6. **COPY замість ADD**
   ```dockerfile
   COPY . /app  # Замість ADD . /app
   ```
   **Чому:** ADD автоматично розпаковує архіви - непередбачувана поведінка.

7. **Фіксація версій**
   ```dockerfile
   FROM python:3.11.7-slim  # Замість python:latest
   ```
   **Чому:** Передбачуваність та стабільність.

### 4. Які порушення є критичними для безпеки?

#### 🔴 **КРИТИЧНІ (Блокують деплой):**

| Порушення | Наслідок | Рівень ризику |
|-----------|----------|---------------|
| **Запуск від root** | При зломі додатку зловмисник отримує root-права в контейнері та потенційно на хості | 🔴 CRITICAL |
| **Секрети в образі** | Паролі/ключі стають доступні всім, хто має доступ до образу | 🔴 CRITICAL |
| **Використання latest тегів** | Непередбачувані зміни, можливі несумісності | 🔴 HIGH |

#### 🟡 **ВАЖЛИВІ (Мають бути виправлені):**

| Порушення | Наслідок | Рівень ризику |
|-----------|----------|---------------|
| **Відсутність HEALTHCHECK** | Неможливо автоматично виявити "мертві" контейнери | 🟡 MEDIUM |
| **Великий розмір образу** | Довше завантаження, більше потенційних вразливостей | 🟡 MEDIUM |
| **ADD замість COPY** | Непередбачувана поведінка при копіюванні архівів | 🟡 LOW-MEDIUM |

### 5. Як змінюється поведінка pipeline при різних рівнях помилок?

#### **Стратегія 1: Строгий контроль (Production)**
```yaml
hadolint:
  allow_failure: false  # Блокує при будь-яких проблемах

trivy:
  allow_failure: false  # Блокує при вразливостях

dockle:
  allow_failure: false  # Блокує при порушеннях CIS
```
**Результат:** Максимальна безпека, але можливі блокування деплою.

#### **Стратегія 2: Поступове впровадження (Development)**
```yaml
hadolint:
  allow_failure: true   # Попереджає, але не блокує

trivy:
  allow_failure: false  # Блокує тільки критичні проблеми

dockle:
  allow_failure: true   # Попереджає про покращення
```
**Результат:** Баланс між безпекою та швидкістю розробки.

#### **Стратегія 3: За рівнями severity**
```yaml
trivy:
  script:
    - trivy config --severity HIGH,CRITICAL --exit-code 1 Dockerfile
  # LOW та MEDIUM не блокують
```
**Результат:** Блокуються лише критичні проблеми.

### 6. Чому важливо запускати всі три інструменти?

Кожен інструмент покриває свою область безпеки:

```
┌─────────────┐
│  Hadolint   │ → Ловить синтаксичні помилки та порушення стилю
└─────────────┘   (швидко, на етапі написання коду)
       ↓
┌─────────────┐
│   Trivy     │ → Виявляє конфігураційні вразливості
└─────────────┘   (глибокий аналіз безпеки)
       ↓
┌─────────────┐
│   Dockle    │ → Перевіряє production-готовність
└─────────────┘   (CIS benchmarks, оптимізація)
```

**Приклад:**
- Hadolint виявить використання `ADD` замість `COPY` ✓
- Trivy виявить запуск від root (критична вразливість) ✓✓
- Dockle перевірить відповідність CIS стандартам ✓✓✓

**Разом вони дають 100% покриття безпеки.**

Якщо використовувати лише один інструмент:
- ❌ Hadolint не виявить відсутність користувача
- ❌ Trivy не перевіряє стиль коду
- ❌ Dockle не фокусується на вразливостях

### 7. Як створити Dockerfile, щоб він був безпечний і пройшов перевірки?

#### **Покроковий чеклист:**

**Крок 1: Вибір базового образу**
```dockerfile
✅ FROM debian:12.5-slim
✅ FROM python:3.11.7-alpine
❌ FROM ubuntu:latest
```

**Крок 2: Додавання метаданих**
```dockerfile
LABEL maintainer="team@example.com"
LABEL description="Secure web application"
```

**Крок 3: Встановлення пакетів (один шар!)**
```dockerfile
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
      curl \
      ca-certificates && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*
```

**Крок 4: Створення користувача**
```dockerfile
RUN useradd -m -s /bin/bash appuser
USER appuser
```

**Крок 5: Копіювання файлів**
```dockerfile
COPY --chown=appuser:appuser app/ /app/
```

**Крок 6: Додавання HEALTHCHECK**
```dockerfile
HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
  CMD curl --fail http://localhost:8080/health || exit 1
```

**Крок 7: Налаштування запуску**
```dockerfile
CMD ["python3", "-u", "app.py"]  # Exec form!
```

## 🎓 Ключові уроки

1. **Автоматизація є критичною** - Ручна перевірка неефективна і ненадійна.

2. **Безпека - це багатошаровий процес** - Один інструмент не покриває всіх аспектів.

3. **Найкритичніша проблема - root** - Завжди створюйте непривілейованого користувача.

4. **CI/CD дозволяє гнучко налаштовувати строгість** - Можна поступово впроваджувати нові правила.

5. **Production-образ вимагає дотримання множини практик** - Від вибору базового образу до HEALTHCHECK.

6. **Розмір образу впливає на безпеку** - Менший образ = менше вразливостей.

7. **Кожна проблема має рівень критичності** - Важливо розуміти пріоритети.
